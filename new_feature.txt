# FocusFlow — Commitment Lock / Focus Contract Feature

You have already implemented the FocusFlow Android application based on the previous specification.

Now extend the existing application with a major new feature called **Commitment Lock**.

Do NOT rebuild the application from scratch.

Do NOT replace the existing architecture.

Do NOT remove or break existing functionality.

Integrate this feature cleanly into the current Kotlin + Jetpack Compose + MVVM/Clean Architecture + Room + Firebase + Coroutines/Flow + WorkManager architecture.

The feature should make FocusFlow significantly more unique:

> Users voluntarily create a commitment around a task. If they fail to complete the commitment before the deadline, FocusFlow activates a user-selected consequence, such as restricting access to selected distracting apps where technically and policy-wise supported.

The feature should be designed as a core productivity/accountability system rather than simply an "app blocker."

---

# 1. Product Concept

Introduce:

## Commitment Lock

The philosophy is:

> **You decide the consequence before you start.**

Example:

The user creates:

Task:
"Complete ML Assignment"

Deadline:
8:00 PM

Estimated duration:
2 hours

The user enables:

**Commitment Lock**

Then chooses:

* Which distracting apps to restrict
* What happens when the deadline is missed
* How the restriction can be released
* Whether an emergency cancellation is available

The user explicitly confirms the commitment before it becomes active.

# 2. Important Android / Google Play Constraint

This feature MUST be implemented with Android and Google Play policies in mind.

Do NOT secretly disable, uninstall, modify, or interfere with other applications.

Do NOT attempt to bypass Android security mechanisms.

Do NOT make FocusFlow impossible for the user to recover from.

Do NOT use AccessibilityService merely as a hidden mechanism to control other apps.

If AccessibilityService is considered, first structure the feature around:

* Prominent disclosure
* Explicit user consent
* Clear explanation of what the service does
* Appropriate Android implementation
* Google Play policy compliance
* Play Console declaration requirements

If a particular app-restriction mechanism is not suitable for ordinary consumer Google Play distribution, do NOT force it into the implementation.

Instead:

1. Build the complete Commitment Engine and UI.
2. Create a clean abstraction for the restriction mechanism.
3. Implement the strongest policy-compliant mechanism available for the target Android version/device.
4. Provide a graceful fallback if actual app restriction cannot be performed.
5. Clearly communicate limitations to the user.

The product must remain publishable.

Create an abstraction such as:

`AppRestrictionManager`

so the rest of the application does not depend directly on a particular Android restriction API.

Example conceptual interface:

```kotlin
interface AppRestrictionManager {

    suspend fun getAvailableApps(): List<RestrictableApp>

    suspend fun enableRestriction(
        apps: List<String>,
        reason: String
    ): RestrictionResult

    suspend fun disableRestriction(
        apps: List<String>
    ): RestrictionResult

    suspend fun isRestrictionActive(
        packageName: String
    ): Boolean
}
```

Adapt this interface to the actual Android APIs and capabilities available.

Recommended states:

```text

  ↓

  ↓
```

```text

  ↓

  ↓

  ↓

  ↓

```

Possible terminal/cancellation states:

```text

EXPIRED
```

Create an enum/sealed model appropriate to the architecture.

Example conceptual states:

```kotlin
enum class CommitmentStatus {

    WARNING,
    COMPLETED,
    MISSED,
    RESTRICTED,
    RECOVERY,
    CANCELLED,
    EXPIRED
}
```

Do not duplicate state logic throughout multiple screens.

Create a centralized Commitment Engine/use case layer.

1. User completes the task one second before deadline.
2. User completes the task exactly at deadline.
3. Device is offline when deadline occurs.
4. Device is powered off at deadline.
5. Device restarts.
6. WorkManager job is delayed.
7. User changes device time.
8. User changes timezone.
9. User changes the task deadline.
10. User deletes the task.
11. User deletes an app selected for restriction.
12. Selected app is not available.
13. Restriction permission is revoked.
14. Android version does not support the required mechanism.
15. User logs out.
16. User logs into another account.
17. Multiple commitments overlap.
18. User has multiple missed commitments.
19. User completes recovery.
20. User cancels a commitment.
21. Firebase synchronization fails.
22. Room database contains stale data.

Never allow inconsistent commitment state.

Use server timestamps or trusted time sources where appropriate, and protect against obvious local clock manipulation without making the app unusable.

# 39. Restriction Conflict Logic

If:

Commitment A restricts YouTube until Task A is completed.

Commitment B restricts YouTube until Task B is completed.

Completing Task A must NOT immediately restore YouTube if Task B is still active.

Conceptually:

```text
YouTube restrictions:

Commitment A → ACTIVE
Commitment B → ACTIVE

Result:
YouTube remains restricted.
```

Only restore when:

```text
Commitment A → COMPLETE
Commitment B → COMPLETE
```

This should be handled by a centralized restriction coordinator.

* Task models
* Repositories
* Navigation
* Notification systems
* AI clients
* Database infrastructure
